# Задание 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

## Задание 10.1. Какие коллекции данных переводить на Cassandra в первую очередь?

Начинать переход на Cassandra имеет смысл с тех коллекций данных, которые предполагают частые записи:
1) `Cart`: здесь обновление данных будет происходить чаще всего;
2) `ProductStock`: коллекция будет на втором месте по частоте обновлений;
3) `Order`: также будет обновляться достаточно часто.

Для коллекции `Product` есть проблема: фильтрация и сортировка по цене в Cassandra поддерживается весьма слабо.
Варианты есть (Price Bucketing или Multi-Table Strategy для каждого варианта поиска/сортировки), но проще всего оставить её в MongoDB.
Но: стратегию шардирования нужно изменять, чтобы товары более равномерно были распределены по шардам. Например, без затей шардировать по `_id`, а на категорию добавить только хеш-индекс.

Коллекции-справочники тоже можно оставить в Mongo DB.

## Задание 10.2. Концептуальные модели данных для Cassandra

### 1. Таблица Cart (Корзины)

```cql
CREATE TABLE carts (
    client_id UUID,
    session_id UUID,
    cart_id UUID,
    status TEXT,
    created_at TIMESTAMP,
    updated_at TIMESTAMP,
    expires_at TIMESTAMP,
    product_id UUID,
    quantity INT,
    PRIMARY KEY ((client_id, session_id), created_at, cart_id)
) WITH CLUSTERING ORDER BY (created_at DESC, cart_id ASC);
```

**Partition Key**: `(client_id, session_id)` - составной ключ для распределения корзин по узлам
**Clustering Key**: `created_at DESC, cart_id ASC` - сортировка по времени создания (новые первыми) и ID корзины

**Обоснование выбора ключей**:
- **Partition Key** обеспечивает равномерное распределение данных и позволяет быстро находить корзины конкретного пользователя или сессии
- **Clustering Key** позволяет эффективно получать последние корзины пользователя и обеспечивает уникальность записей

### 2. Таблица ProductStock (Запасы товаров)

```cql
CREATE TABLE product_stocks (
    product_id UUID,
    warehouse_id UUID,
    quantity INT,
    updated_at TIMESTAMP,
    PRIMARY KEY (product_id, warehouse_id)
);
```

**Partition Key**: `product_id` - распределение по товарам
**Clustering Key**: `warehouse_id` - группировка запасов одного товара по складам

**Обоснование выбора ключей**:
- **Partition Key** по `product_id` позволяет быстро получить все запасы конкретного товара на всех складах
- **Clustering Key** по `warehouse_id` обеспечивает эффективный доступ к запасам товара на конкретном складе
- Такая структура оптимальна для частых операций проверки и обновления запасов

### 3. Таблица Orders (Заказы)

```cql
CREATE TABLE orders (
    client_id UUID,
    created_at TIMESTAMP,
    order_id UUID,
    status TEXT,
    total_sum DECIMAL,
    dest_location_id UUID,
    PRIMARY KEY (client_id, created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC, order_id ASC);

-- Дополнительная таблица для товаров в заказе
CREATE TABLE order_items (
    order_id UUID,
    product_id UUID,
    quantity INT,
    price_per_item DECIMAL,
    PRIMARY KEY (order_id, product_id)
);
```

**Основная таблица Orders**:
- **Partition Key**: `client_id` - распределение заказов по клиентам
- **Clustering Key**: `created_at DESC, order_id ASC` - сортировка по времени создания (новые первыми)

**Таблица Order Items**:
- **Partition Key**: `order_id` - группировка товаров по заказам
- **Clustering Key**: `product_id` - уникальность товаров в заказе

**Обоснование выбора ключей**:
- **Partition Key** по `client_id` обеспечивает быстрый доступ к истории заказов конкретного пользователя
- **Clustering Key** по времени позволяет эффективно получать последние заказы пользователя
- Разделение на две таблицы следует принципам денормализации Cassandra и оптимизирует запросы

### Преимущества данной модели для Cassandra:

1. **Высокая производительность записи** - оптимизировано для частых обновлений корзин и запасов
2. **Эффективное распределение данных** - partition keys обеспечивают равномерную нагрузку на узлы
3. **Быстрые запросы по ключам** - структура ключей соответствует основным паттернам доступа к данным
4. **Масштабируемость** - легко добавлять новые узлы без перебалансировки данных


## Задание 10.3. Обеспечение целостности данных в Cassandra

| Коллекция | Hinted Handoff | Read Repair | Anti-Entropy Repair | Обоснование |
|-----------|----------------|-------------|---------------------|-------------|
| **Cart** | ✅ Включить | ❌ Отключить | ❌ Не требуется | **Временные данные**: Hinted Handoff достаточен для предотвращения потери записей при сбоях узлов. Read Repair избыточен для некритичных данных корзин. Anti-Entropy не нужен - корзины живут максимум неделю и автоматически удаляются по TTL. |
| **ProductStock** | ✅ Включить | ✅ Включить | ✅ Высокая частота (ежедневно) | **Критичная консистентность**: Неточные данные о запасах могут привести к overselling. Все механизмы должны работать активно. Частый Anti-Entropy Repair необходим для выявления расхождений в критически важных данных о запасах. |
| **Order** | ✅ Включить | ✅ Включить | ✅ Высокая частота (ежедневно) | **Финансовые данные**: Заказы содержат информацию о платежах и должны быть абсолютно консистентными. Потеря или искажение данных заказа недопустимы. Все механизмы восстановления должны работать максимально активно. |


### Детальное обоснование стратегий:

#### **Hinted Handoff** (Отложенная передача)
- **Cart**: Обязательно - предотвращает потерю обновлений корзины при временной недоступности узлов
- **ProductStock**: Критично - каждое обновление запасов должно быть доставлено для предотвращения overselling
- **Order**: Критично - потеря данных заказа недопустима с финансовой точки зрения

#### **Read Repair** (Восстановление при чтении)
- **Cart**: Отключить - избыточно для временных некритичных данных, создает ненужную нагрузку
- **ProductStock**: Критично - гарантирует получение актуальных данных о запасах при проверке
- **Order**: Критично - история заказов должна быть консистентной при каждом запросе

#### **Anti-Entropy Repair** (Профилактическое восстановление)
- **Cart**: Не требуется - корзины живут максимум неделю и удаляются по TTL, repair не успевает принести пользу
- **ProductStock**: Часто - регулярная проверка целостности критически важных данных о запасах
- **Order**: Часто - финансовые данные требуют регулярной верификации целостности

### Рекомендуемые настройки консистентности:

```cql
-- Для критических операций с запасами и заказами
CONSISTENCY QUORUM;

-- Для операций с корзинами (менее критично)
CONSISTENCY ONE;
```

**Обоснование уровней консистентности**:
- **QUORUM** для ProductStock и Order обеспечивает строгую консистентность критических данных
- **ONE** для Cart обеспечивает высокую производительность при приемлемом уровне консистентности для пользовательских корзин
